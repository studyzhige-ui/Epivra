# Epivra 技术详解

**源码基线：** [9a0861b](https://github.com/studyzhige-ui/Epivra/tree/9a0861bd195ca8d1eafa04613c1ea9021d2ab0eb)（v0.3.6）

这份教材解释 Epivra 为什么需要各项机制，以及模型、Agent、运行时、工具、证据、数据库和执行环境如何协作。以实际源码为依据，但不以逐个文件、函数或字段的顺序组织正文。

阅读路线从一项研究的生命周期开始，先建立全局模型，再追踪 Agent 的每轮执行、多个 Agent 的协作、资料获取与证据形成、报告校验，最后讨论长任务可靠性、验证和维护。

> **阅读约定：** “当前实现”专指上述源码基线；举例用于解释程序的行为，不代表实际运行结果。重要机制以源码及可核查的状态变化为准。方案与实现、调用成功与结果正确、持久化与模型记忆均需要区分。

## 学习范围

**Agent 核心：** Agent Loop；工具系统的定义、发现、授权、执行、结果与恢复；上下文装配、预算、隔离、压缩与检查点；任务级工作记忆与通用长期记忆的边界；主从多 Agent 的角色、任务、交接、协同、结果聚合及状态治理。

**支撑工程：** 模型适配、网络请求、文件与结构化数据处理、异步执行、并发控制、事务存储、可追溯记录、受限分析、日志与诊断。只解释理解 Epivra 所需的基础原理，不在项目教材中重复完整的 Python、SQL、Redis 或操作系统课程。

**事实边界：** Epivra 并未实现跨研究的完整长期记忆系统、通用 Agent 动态发现网络或任意层级递归委派。介绍这些概念时，应说明它们属于通用知识或可能的替代架构，而非当前项目功能。

## 正文写作与证据规则

本教材首先是**Epivra 的工程技术详解**，不是对 Agent 能力的中立选型清单，更不是产品限制汇总。每一节应从项目真实要解决的问题出发，说明为什么采用这一设计、多个机制如何共同实现目标，以及关键机制在源码里怎样发生；真正改变使用者理解或系统正确性的设计边界，才需要在相应位置清楚说明。

- **以项目为主语：** 先写 Epivra 已实现的设计及其作用，不用“某项技术也许有用、也许没用”的泛泛讨论替代具体机制。正面陈述价值，不夸大成未经验证的性能、准确率或绝对保证。
- **从官方工程资料补充设计依据：** 每章主动查阅与本章机制直接相关的高质量原始资料，优先官方技术文章、框架文档、协议规范或可靠研究论文。提炼能帮助建立原理、组织因果关系和说明架构取舍的论据；正文可按需附来源链接，不堆砌文献。不能仅靠主观印象或照搬旧稿完成章节。
- **分清三类陈述：** 以 Epivra 固定源码验证“当前怎样实现”；以公开技术资料支持“这种机制为什么合理”；以项目实际评测证明“Epivra 取得了怎样的效果”。不可把第三方的实验结果、通用框架特性写成 Epivra 自己的实测成绩或已有功能，也不要凭后来的外部文章臆测开发者过去的真实动机。
- **把相互关联的机制讲成系统：** 例如多 Agent 不仅属于协作架构，也通过独立 Work 上下文、聚焦交接与来源回读参与上下文治理。章节应该展示这些因果连接，而非把每个术语孤立放在清单里。
- **用读者的阅读顺序组织解释：** 问题 → 必要概念 → 机制和状态推演 → 源码落点 → 设计价值及必要边界。复杂处配图和示例，简单处自然段即可。图表应帮助理解拓扑、状态、依赖和异常路径，不复述方框与箭头；减少对代码文件和字段的逐项罗列。
- **全书以知识完整性而非篇幅为目标：** 保留真实重要机制及所必需的后端基础；一个概念选择主要章节深入讲透，其他章节引用并推进新知识，不重复讲同一段道理。
