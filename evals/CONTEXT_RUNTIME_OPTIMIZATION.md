基线：`cc0d68d89981aa0730d1bf6fbbdd9bf511ede777`。全部改动只累积到 `improve/epivra-optimization`，不是发布验收结论。

## 已实施的通用改动

### 1. 上下文装配不再反复序列化已经接受的内容

`context.assemble` 原实现每加入一个候选，都重新编码必需指令、全部已选正文与元数据；窗口接近容量时，又对每个回读句柄重复编码。新实现根据既有 compact JSON 编码计算增量长度，只编码当前候选与最终请求。

保留原本的排序、直接输入优先、澄清优先、原文句柄、memory、真实 omitted_count 及其十进制位数增长时的回退行为。没有改提示词、资料选择策略、权限、模型、模型上下文容量或用户原始要求。最终仍进行一次精确序列化检查。旧实现仅作为 `evals/context_assembly_reference.py` 的冻结比较对象，不是第二套生产运行时。

### 2. 修复导航最后一项的实际 envelope 容量

旧 `page` 用整数 next_offset 检查容量，之后可能把它换成 JSON null，导致结果反而超过既有容量。最小反例：`[{"ref":"r","value":""}]` 在71字符容量下返回74字符。新实现按真实最终游标计数，并在连空元数据都放不下时显式失败；没有放宽容量或截断原始材料。正常顺序与回读句柄保留。

上述容量均指已有的模型输入/导航协议容量，**不是报告篇幅限制**。

### 3. 避免同一 PR 提交重复启动两份离线矩阵

原 `on: [push, pull_request]` 在本分支一次提交触发两份14-job矩阵，例如35440901739和35440903243。现在保留所有 PR、main push 和显式手动验证；开发分支未开PR时需主动运行验证。不减少矩阵、测试、安装检查或类型检查。只取消同一离线工作流/事件/ref的过期运行，不修改付费工作流或其取消策略。

开发边界继续记录在评测文档中，不注入研究角色 prompt，也不覆盖仓库忽略的本地 AGENTS 文件。产品不存在默认报告字数、字符、段落或章节数量限制。用户明确写作要求继续作为原始任务输入，不变成题材规则或普遍长度门槛。普通小型真实测试已获授权；十题或同等昂贵批量测试仍须明确审批，不拆分绕过。

## 已定位、尚不能用单案例修改的研究问题

基于已有联网运行35436729675的公开成果：

1. seq960的调查成果把后续异常日志判断标为inference。seq1713初稿及seq3928终稿仍将其与文档引用并列，最终seq4927 review接受。原始标签确实存在，所以不能简单归因于没有结构化findings。
2. 叶子异常的更强一般化表述出现在作者稿件，最终核查没有拦住。后续应测试“来源陈述→推断→成稿→核查”是否保留证据强度，并加入成立推断、无依据推断与无关语言改写的对照。
3. 现有导出不能可靠分解完整任务的本地与供应商耗时。继续进行昂贵全题复测之前，需要在真实调用路径记录可关联的阶段时间；并发span要保留重叠，不能直接累加为用户等待时长。

这些是已记录的传播路径和待验证的一般机制，**没有据此加入Python专用指令、强制代码执行、更多reviewer、首回合强制委派或新的报告写作限制**。证据定位：[research-trace.json](evidence/context-20260919/research-trace.json)。它引用旧运行，不冒充本轮重新执行或新版本质量改善。
